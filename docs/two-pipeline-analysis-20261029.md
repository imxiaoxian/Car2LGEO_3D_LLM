# 两套乐高生成方案分析

核对日期：2026-10-29。分析对象是两个独立项目，不是 LLM 项目内部的 Codex / LoRA 规划器比较。

后续决定：用户选择将两套能力整合到 `Car2LGEO_3D_LLM`，在完成备份、迁移和验证后删除旧仓库及本地副本。下文的独立仓库建议保留为当时的架构分析；当前实现见 [统一工作流](unified-workflows.md)，不再要求维护两个活动仓库。

## 结论

面向带机构的汽车及后续通用物品，建议优先发展第二套的语义装配规划和真实连接工具。
第一套保留为多视图几何重建路线及独立对照。这个研发优先级来自架构适配性，
不是已经通过同输入整车实验得出的质量排名。两套都尚未证明完整汽车的交付质量。

## 优点与代价

| 维度 | 第一套：多视图重建 | 第二套：LLM + Blender |
| --- | --- | --- |
| 外形来源 | 联合图像条件提供整体几何约束；受视图一致性和重建误差影响 | 语义模块和参考图约束建模；能定向修补，但可能偏离图像或产生不一致边界 |
| 零件与机构语义 | 网格不直接表达轴、孔、门铰链和搭建关系 | 场景保留模块、父子关系、关节与设计接口，便于进一步规划 |
| 修改能力 | 改网格或配方参数；固定拓扑限制变化 | 可以局部修改对象、接口和子装配；需要版本检查及回滚 |
| 主要资源 | 本地重建模型、显存、图像服务；下游仍可能有模型评审调用 | 图像服务、多轮模型调用、Blender 和原生检查；调用成本与耗时波动较大 |
| 能力边界 | 有限车型家族、原生轮组和玻璃选择；分类目录不等于实现覆盖 | 已有原生连接工具和局部代理闭环；模块组合、承载与整车仍不充分 |
| 复现条件 | 权重、代码、随机种子、图像和网格均需固定 | 还需固定模型、协议、工具实现、上下文、语料及每步操作记录 |

未取得当前两套完整流程的同条件时间、成本和质量基准，不给出速度倍数或成功率排名。
第一套也使用 GPT 图片和相关模型服务，不能将整条流水线称为完全离线。

## 共同瓶颈

连续网格到离散装配的转换，是两套方案共同的关键问题。更精细的网格并不自动产生
更合理的乐高拓扑；更多语义名称也不能保证零件兼容、轴向防脱、结构承载或搭建顺序。

第一套 `recipes.py` 明确约束零件架构与车身参数；第二套的旧装配路线仍有同类限制。
因此只替换上游重建模型，可能仍得到相似的配方化车身。约 1:12 的目标也受实际
轮组、玻璃和底盘架构能力约束，不能通过缩放标准零件补齐。

第二套 `staged_model.py` 的 Blender 接口标为 `design-inference`，不是测量得到的
标准 LEGO 连接器。真正拼装必须落到原生 `.dat` 几何、`.conn` 连接点和 `.col` 碰撞体，
再独立检查运动、外观与归档。

### 四轮底盘的轴向退出诊断

后续对上述底盘的原始 `assembly/model.io` 做了只读诊断，报告位于
`runs/open-source-optimization-20261029/autonomous-chassis-axial-diagnostic-v2/report.json`。
源归档与诊断图均未改写，四个轮组的检查均没有缺失碰撞体或初始跨模块碰撞。

四个轮组结果一致：沿各自源连接器轴的正方向（本装配中为向外），到所选轴孔完全脱离的
20.25 LDU（8.1 mm）全程没有碰撞体阻挡；反方向在 26.35 LDU 处开始受到轮胎与底板的
几何阻挡。这是原生碰撞体及 0.35 LDU 容差下的刚性直线平移结果，不包含卡扣弹性、摩擦、
拔出力或承载。连接器端部标记也没有被当成不存在的几何挡止。

因此，现有运动通过结果不能升级为双向几何防脱通过，更不能据此推断轮组实物会自行脱落。
下一步应比较具有真实挡肩、轴套或其他限位结构的候选，分别验证轴向约束、转动间隙和
装配可达性；双向阻挡本身仍不等于承载或实物验收。当前尚无完成此项验证的新轮组结果。

后续显式双轴套夹具 `dual-bush-candidate-v3` 已完成静态、9 姿态运动、六视图和 IO 往返：整个轮组在采样姿态下双向阻挡，但独立轴、内轴套及轮毂仍有退出路径。它是人工指定零件和坐标的诊断夹具，不是代理自主设计，也没有解决内部零件防脱、装配次序或承载。

## 如何使用开源参考

| 参考 | 适合吸收的部分 | 接入限制 |
| --- | --- | --- |
| LEGO Forge | 可复用子装配、可定位诊断、实际渲染后的评审与修复、易检查的交付物 | 固定版本检查器跳过同组碰撞并直接连接组内零件；其 PASS 不能替代汽车连接与运动验收 |
| BrickAgent / BrickBench | 真实连接器驱动放置；将外观、机械有效性和稳定性分开评估 | 本地普通碰撞或地面支承检查不等同于其 PyBullet 稳定性模拟 |
| BrickWright / BrickLayer SDK | 在导出后的实际零件上做独立碰撞、悬空、连通复核 | 原生轮胎/轮毂与 SDK 碰撞判定存在差异，尚无自动裁决 |

来源地址和核验提交固定记录于 `open-source-assembly-references.md`，避免随默认分支变化。

## 两套各自的优化重点

第一套优先保留输入轮廓与关键特征，减少配方强行改写车顶、轮拱、门窗的情况；
把真实连接、碰撞和尺寸能力检查前置到候选选择。用同一网格做转换算法对照，
才能区分重建问题和装配问题。保持本项目独立环境与证据。

第二套优先从已验证轮组推进到有明确接口的底盘组合，加入轴向防脱、受力路径与
运动间隙检查，再接车身和门窗。规划器负责选择和组合，宿主负责精确连接、检查、
回滚及导出；避免让模型自行手算全部位姿。单模块成功后应推进组合任务，
不靠重复相同轮组试验推断整车能力。

两套均优化时，建议保持各自上游和运行环境独立，使用一致的装配验收规范比较下游结果。
第一套固定网格，比较现有配方与保留轮廓、关键部位约束的转换候选；第二套固定任务和
零件库，沿“防脱与受力路径 → 转向底盘 → 车身接口及门窗 → 完整汽车”推进。
这些是后续优化顺序，不是已经实现的新能力。

通用物品扩展需要把任务规格从车辆专用轴距、四轮和门窗规则，扩展为可配置的
功能、模块接口、外观目标及结构条件，并覆盖建筑、家具、动物和器物等独立留出类别。
这是后续设计方向，不是现有通用能力声明。

## 公平比较方式

固定相同物体身份、参考图、目标尺寸、功能需求、零件库版本及验收规则，
分别运行两套项目。对默认配方路线和显式装配代理路线分别记录，避免混淆变量。

比较最终原生零件模型的轮廓与关键部位、碰撞和连通覆盖、机构运动、修复次数、
端到端时间、模型调用成本及 IO 往返。Studio 打开与实体搭建单独记录。
首轮汽车通过后再用未见车型和非汽车物体检验泛化；结果不完整时保持无胜者。

本次补充分析核对的是本地当前工作目录、已有报告与固定提交的 Forge 源码。两套本地目录
均有未提交修改，以上能力不能直接视为 GitHub 默认分支已经具备。未重新运行收费生成、
完整汽车基准或实体拼装；历史报告的耗时也不是两套完整流程的公平性能比较。
