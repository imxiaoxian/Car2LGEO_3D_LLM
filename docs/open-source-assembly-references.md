# 开源装配方案对照与接入

2026-10-29 对照用户提供的帖子、三张参考图和 LEGO Forge 仓库，核验实际公开源码。
这里比较两套本地方案，并记录本仓库对开源装配研究的接入。两套能力现已整合到本仓库，
以下独立项目描述保留研究时的历史上下文；当前路由与边界见 [统一工作流](unified-workflows.md)。

两套项目的架构取舍、各自优化重点和同输入比较方法见
[两套方案分析](two-pipeline-analysis-20261029.md)。

## 两套本地方案

| 方案 | 主要生成路径 | 优点 | 当前限制与适用边界 |
| --- | --- | --- | --- |
| [Car2LEGO_3D](https://github.com/imxiaoxian/Car2LEGO_3D) | 四视图图像 → Hunyuan3D-2mv 联合网格 → 物理尺寸校准 → 乐高零件装配 → Studio `.io` | 外形由多视图网格约束；适合外形相似度优先、已有多视图素材的重建任务 | 网格重建不提供乐高拓扑、机械接口或可拼装性；后续离散成零件和机构验证是独立难题，且依赖本机原生零件服务 |
| [Car2LGEO_3D_LLM](https://github.com/imxiaoxian/Car2LGEO_3D_LLM) | GPT 多视图/特写 → 语义模块 → LLM + Blender 分阶段建模 → 原生乐高装配及 Studio `.io` | 可表达门、玻璃、车架和运动机构等语义关系；能够定位、修补实际 Blender 对象和原生连接点 | 对任务上下文、零件选择和连接规划要求高；已完成描述选件单轮组及从空场景自主选件的 17 件四轮底盘闭环，尚未证明防脱、承载、整车或未见零件泛化 |

两者不是同一生成器的两个规划器，也不能用其中一个的通过状态代替另一个的质量验收。
对汽车任务，推荐先在 LLM + Blender 方案中打通原生滚动轮组和承载模块，再逐步验证底盘、
转向/悬挂及整车；多视图重建继续作为外形参考和独立重建路线。对“所有物品”，需要扩展
零件语义、任务规格和机械/外观验收，汽车单模块结果不能外推为通用生成能力。

## 已核验的来源

| 来源 | 实际实现及检查版本 | 本次采用的做法 |
| --- | --- | --- |
| [BrickWright](https://github.com/AvaLovelace1/brickwright)；[论文](https://arxiv.org/html/2610.31651v1) | `dc9beb7b5391a272d96339695cc5a842bd1459de`；运行依赖固定 `bricklayer-sdk==0.1.0` | 实际调用 SDK，对最终原生零件做独立碰撞、地面支承、连接分量复核 |
| [BrickBench / BrickAgent](https://github.com/kulits/BrickAgent)；[论文](https://arxiv.org/html/2610.12452v1) | `b3df55e36c669b22ef089b13db1ee841907d09b3`；官方环境名为 BrickAgent | 按真实连接点安装零件，避免让规划器手写平移矩阵；协议有明确输入和原子回滚 |
| [LEGO Forge](https://github.com/ericfu-tianchi/lego-forge) | `dd9258eea722417f7029001b20459f1610a9ec12` | 将问题定位到零件编号、原生位置；保留检查、渲染、评审、修复的分层证据 |
| [Emm 原帖](https://x.com/emmanuel_2m/status/2096377028945576370) | X 官方 oEmbed 已返回作者、原型描述和 2026-09-05 日期；长正文未完整取得 | 作为交互和交付参考。尚未核验到该原型对应的公开源码，不称为已复现开源实现 |

BrickBench 与 GitHub 上同名游戏地图编辑器无关。其官方 README 明确使用 BrickNet 连接器、
凸碰撞体和 PyBullet 稳定性模拟；本次没有把地面支承检查称为同等的物理稳定性模拟。

Forge 的 `engine/check.mjs` 主要使用格列/包围盒和 stud/anti-stud 规则，并对同一 `group`
跳过碰撞、直接建立内部连通边。因此没有将其 PASS 直接接作车辆机构验收，也没有照搬
300 件下限、2000 件上限或建筑配色要求到车辆任务。参考的是具体诊断和迭代方法。

## 两套项目的独立复核

各项目都有自己的 `car2lego3d.bricklayer_audit`，不跨项目导入代码或运行环境。
适配器在子进程中调用 BrickLayer 的 `from_ldraw`、`colliding_placements`、
`floating_placements` 和 `connected_components`。输入是实际导出的平铺 LDraw；
原始文件不改写。JSON 记录输入 SHA-256、SDK 版本、全部问题计数、最多 100 项的定位
信息和限制。原生 FCL 崩溃、超时、缺依赖、跳过零件、导入警告和校验期间源文件变化
均不能产生完整通过。部分导入的索引明确标为子集，不能错误映射回原始整车。

- LLM 项目：`AssemblyTools.check` 复核实际世界变换的零件图；常规 Studio 导出也复核平铺后的实际模型。检查摘要向模型提供独立状态和问题数量，完整记录可分页查看。
- 重建项目：`reservation.audit_assembly` 复核实际装配，优化候选和 Studio 导出保存报告。严格模式下，独立检查不通过的候选不能被选为最佳方案。优化缓存绑定校验实现、SDK 版本和模式，避免继续使用接入前的旧评分。

在各自项目目录安装：

```powershell
uv pip install --python .venv/Scripts/python.exe bricklayer-sdk==0.1.0
```

可选依赖组也已声明为 `.[brickwright]`。模式通过进程环境传入：

```powershell
$env:CAR2LEGO_BRICKLAYER_AUDIT = 'auto'
```

`auto` 在 SDK 可用时保存交叉诊断，不自动替换原生判定；`required` 将独立结果作为额外门槛，
缺依赖或覆盖不完整同样阻止通过；`off` 关闭复核。SDK 不可用的 auto 模式明确记录不可用，
不会把未执行的检查写成 pass。模式不会偷偷切换建模或装配规划器。

单独复核已有模型：

```powershell
.venv/Scripts/python.exe -m car2lego3d.bricklayer_audit --source path/to/model.ldr --output runs/independent-audit.json --library 'D:/lego/Studio 2.0/ldraw'
```

该命令默认严格检查，未通过时退出码为 1，详细报告仍保存。

## LLM 连接点安装工具

`assembly-tools.v9` 提供 `attach`、批量 `build`、已有模块的 `search_mounts` 和子装配 `clone`，规划上下文合同当前为
`assembly-context.v20`。`build` 可在单个原子 revision 中组合 module/add/clone/attach/snap，
以 `@alias` 引用本批次实例；默认要求完整原生检查通过，失败会整体回滚。
单独 `attach` 输入当前 revision、真实 part、source_port、target、target_port；可选 parent、color 和
初始刚性 matrix。宿主使用已有原生 snap 计算最终放置，并在一次提交内做完整原生检查。
批量 `build` 将同一机制用于整段子装配，并返回真实 alias 到 instance ID 映射。失败不会遗留
零件、修订号或中间检查点；成功只增加一个修订。初始 matrix 用于轴键滚转等方向选择，
不需要人工计算最终平移。JSON Schema 错误保留完整原文，并附具体字段、操作分支和约束诊断。

`strict=true` 为默认值，拒绝失败或证据不完整的安装；明确未完成的草稿可传 `strict=false`，
之后仍需运行 check。已有模块继续使用 snap，不拆散门板与随门玻璃的子树。
保护模块、版本检查和留出语料规则均沿用现有宿主。

`clone(source,matrix,parent?,color?,alias?)` 复用当前场景中已有的零件或子树。matrix 是新父坐标系下的
刚性位姿；默认保留源根的有效颜色。返回 `clones[].instances` 的源到新实例映射，各副本可独立修改。
内部后代关节保留原父坐标系框架；源根关节连接外部支座，因此不复制，须在新位置 snap、articulate，
再验证整个装配和运动。源模块的验收与车辆绑定不复制；禁止父节点位于源子树内部，严格构建失败整体回滚。
这是对 Forge 可复用子装配思路的本地实现，不豁免副本的连接、碰撞或运动检查。

对同一组真实 3001 零件，新增测试核对 attach 与原来的 add + snap 的 BOM 和世界变换
完全相同，放置操作由两次变为一次。这是工具调用改进，不是整车外观质量提升的实测结论。
新协议与实现哈希会使旧评测失效；没有使用旧 LoRA 或三零件基准宣布新合同下的规划器胜者。
LLM 执行哈希还绑定 SDK 版本和复核模式，切换校验条件后旧评测不能继续作为当前合同证据。
`required` 模式同时拦截常规 Studio 导出和装配代理的 IO 导出，失败诊断仍保留。

## 校准结果与范围

方案取舍：Forge 的图像迭代适合作为“当前模型预览—发现问题—继续修订”的交互模式；
BrickBench 的真实 connector 安装和独立区分机械有效性、外观与可拼搭性，适合作为装配环境合同；
BrickWright 的独立几何检查适合作为第二把校验尺。LLM 项目沿用原生零件和端口，由宿主执行
原子连接、原生检查及实际几何预览，并保留独立审计结果；Forge 的组内碰撞豁免没有用于车辆验收，
BrickBench 的 PyBullet 稳定性能力也没有被本地普通碰撞检查冒名替代。

2026-10-29 的汽车模块探针只证明轮组装配回路的一部分：确定性演示能执行原生连接、检查、
六视图渲染、导出和 IO 往返；它明确标为演示，不算规划器能力。真实 Codex 轮组尝试 v1
没有产生零件并陷入重复读取；v2 查明规划器为 module 操作漏写 `.ldr` 后，面对冗长
`oneOf` 错误没有恢复。v3 加入字段级诊断后成功创建三件模块并通过数字检查及归档往返，
但规划器把仅在一个 build 调用内有效的 alias 当成跨调用实例 ID，反复重建后耗尽修复预算，
未生成预览。v4 明确 alias 作用域及构建后的检查/预览/导出阶段后，完成了真实 preview、
export、finish 和图像反馈；两条工具失败随后分别修复，但 v4 当时的报告仍用“任何错误都失败”
作旧判定，因此其原始 `module_loop_pass=false` 保留不改写。v5 加入首轮与恢复错误的并列字段，
并补正 build 签名导航，真实运行报告 `module_loop_pass=true`、3 件、数字检查 pass、IO 往返
pass，生命周期含 build/check/preview/export/finish，预览图反馈 2 次，初始 context 错误已恢复。
该通过只覆盖这个预定义三件轮组，耗时约 541 秒；不证明自主选件、滚动机构、承载汽车模块、
整车、外观、Studio GUI 或实物搭建。
六张原始预览图均为 480×360，像素方差范围 1930.49–3928.50，且完整几何入镜；它们不是空白图。
规划器对三种零件均保留默认颜色 16，因此轮胎偏白，配色仍未验收。当前错误恢复字段只表示
后续同工具成功，不证明错误参数被逐项纠正；模块通过仍依赖完整生命周期和当前原生检查。
该 v15 历史结果仍是单轮组诊断，不是整车或任意物品生成。后续滚动机构和底盘证据见下节。

## 描述选件与预算控制

`scripts/probe_autonomous_wheel.py` 只提供固定原生支座，不提供移动零件编号或坐标。
代理须搜索英文描述，查询实际几何与连接点，自选轮胎、轮毂和轴，建立移动模块及滚动关节，
完成 check、9 姿态运动、真实预览图像反馈、export 和明确 finish。
验收核对每种新零件在首次放置前的描述检索及原生查询，实际连接边、固定支座未变、
三种角色的原生顶点确实运动，以及 `.io` 中全部装配字段的往返一致性；比较时仅排除
归档来源哈希和修订号。检索中的精确编号提示、失败查询或放置后的补查不能补足选件证据。

`autonomous-wheel-live-v1/report.json` 真实运行约 729.360 秒，26 次决策，
`module_loop_pass=true`、`stop_reason=planner_finished`，无工具错误，代码指纹未变。
代理选择 3704 轴、55982 轮毂和 92402 轮胎；与给定支座共 4 件，原生检查、9 姿态 360°
运动和归档往返通过，预览图像进入后续决策两次。轮胎颜色为 0，轮毂为 7；外观仍未验收。
范围只包括给定支座上的一次描述选件轮组，不代表整车、自主选择支座、未见零件泛化、
轴向防脱、承载、Studio GUI 或实物拼搭通过。

这次运行也暴露了旧检索的数字子串问题：`Tyre 30.4` 返回 32 个混杂尺寸候选，
`Technic Axle 4` 返回 103 个候选，甚至含五长轴。实际选中的二长轴及轮胎也是从混杂结果中
发现，随后通过原生查询核对；因此不能把旧报告解释为尺寸检索已经正确。
现改为保留十进制尺寸并比较完整数值，描述中的 4 不再匹配 40 或零件编号中的 4；
保留显式编号查询及裸编号的花纹变体检索，仍支持 4L 等尺寸后缀。该查询不是尺寸顺序、
单位换算、同义词、配色库存或连接兼容性的推理，选件仍需 query_part 和实际装配检查。
修复后的真实代理复跑使用独立目录，不改写 v1 报告。

`autonomous-wheel-live-v2/report.json` 已完成，约 671.359 秒、29 次决策，
`module_loop_pass=true`、`stop_reason=planner_finished`；无工具错误，执行代码指纹未变。
代理通过描述检索并在放置前查询，选用 3705 四长轴、55982 轮毂与 89201 轮胎。
初次静态检查通过，但运动自适应细分为 33 个姿态后发现轮胎与支座碰撞；代理将移动模块
轴向位置调整到 z=30 LDU，重新检查及 9 姿态 360° 运动通过，原生顶点位移与 IO 往返通过。
